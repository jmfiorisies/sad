!!! tip "Cómo está organizada esta unidad"
    Seguimos con **el edificio**. Ya tiene vigilante (UD3), pasadizo (UD4) y cámaras (UD5). Pero el **propio edificio**
    tiene ventanas abiertas, una **llave maestra** colgada en la entrada y una **puerta trasera** que nadie usa.
    **Bastionar** es cerrar todo eso:

    - **tapiar** lo que no se usa (quitar la superficie de ataque);
    - **quitar la llave maestra** (que nadie entre como `root` sin control);
    - poner **cerrojos** (llaves en vez de contraseñas);
    - un **portero** que apunta al que prueba llaves (**Fail2ban**);
    - un **inspector** que puntúa el edificio (**Lynis**).

    El orden de la unidad:

    1. **Bloque 0:** qué es bastionar y la superficie de ataque.
    2. **Bloque 1:** el ciclo — medir, cambiar, volver a medir — y el inspector (Lynis).
    3. **Bloque 2:** SSH, la puerta principal (sin dejarse fuera).
    4. **Bloque 3:** el núcleo (`sysctl`) y las cuentas (UID 0, SUID).
    5. **Bloque 4:** Nginx, el servicio web.
    6. **Bloque 5:** Fail2ban, el portero.
    7. **Bloques 6 a 8:** las guías (CIS/CCN-STIC), errores típicos y autoevaluación.

    Todo se practica en el **servidor** (`10.10.20.30`) del laboratorio **`docker-sad-ud56`** (el mismo de la UD5). **No
    instalas nada**: `./lab.sh`.

## 📖 0. La superficie de ataque

### 0.1 Un servidor recién instalado… y descuidado

El servidor del laboratorio arranca como un servidor **recién instalado y mal configurado**. Todo esto es **real**,
sacado del laboratorio tal como viene:

| Problema | Cómo se ve |
|---|---|
| `root` entra por SSH con **contraseña** | `sshpass -p bodega2026 ssh root@10.10.20.30 whoami` → `root` |
| Nginx dice su **versión exacta** | `curl -I http://10.10.20.30` → `Server: nginx/1.26.3` |
| Una cuenta **`soporte` con UID 0** (= otro `root`) | `soporte:x:0:0::/root:/bin/bash` |
| Un programa con **SUID** que nadie conoce | `/usr/local/bin/copia-seguridad` |
| **Fail2ban** instalado… sin ninguna cárcel | `Number of jail: 0` |

Cada una es una **puerta o ventana abierta**.

!!! note "Superficie de ataque"
    Es **todo lo que un atacante podría usar para entrar**: puertos abiertos, servicios de más, cuentas, programas con
    privilegios, versiones conocidas con fallos… **Bastionar = reducir la superficie de ataque.**

### 0.2 El ciclo del bastionado

Nunca se cambia todo de golpe. Se hace en un **ciclo**:

```text
   ┌──────────┐      ┌───────────┐      ┌───────────────┐
   │ 1 MEDIR  │ ───▶ │ 2 CAMBIAR │ ───▶ │ 3 VOLVER A    │ ──┐
   │ (Lynis)  │      │ una cosa  │      │   MEDIR       │   │
   └──────────┘      └───────────┘      └───────────────┘   │
        ▲────────────────────────────────────────────────── ┘
```

1. **Medir:** un inspector (Lynis) revisa el servidor y le pone nota.
2. **Cambiar:** una cosa cada vez, comprobando que el servicio **sigue funcionando**.
3. **Volver a medir:** ¿ha subido la nota? ¿hemos roto algo?

!!! danger "Nunca todo de golpe"
    Si cambias diez cosas y algo se rompe, **no sabrás cuál ha sido**. Una cosa, se prueba, y a la siguiente.

## 🔍 1. El inspector: Lynis

**Lynis** es un programa que revisa cientos de cosas del servidor (SSH, contraseñas, núcleo, servicios…) y da una nota:
el **hardening index**, de 0 a 100. Tarda un minuto.

```bash title="./lab.sh lynis   (el servidor como arranca)"
Nota del servidor (hardening index): 58 / 100
Avisos (warning): lo más grave
  TOOL-5104 · All jails in Fail2ban are disabled
Sugerencias de lo que se toca en la UD6 (SSH, Nginx, núcleo, cuentas):
  SSH-7408 · ... · PermitRootLogin (set YES to ...NO...)
  SSH-7408 · ... · MaxAuthTries (set 6 to 3)
  SSH-7408 · ... · X11Forwarding (set YES to NO)
  HTTP-6710 · Add HTTPS to nginx virtual hosts...
(en total: 49 sugerencias; todas en /var/log/lynis-report.dat)
```

| | Qué es | Qué hacer |
|---|---|---|
| **`58`** | el hardening index (la nota, de 0 a 100) | subirla cerrando cosas |
| **`warning`** | lo grave | **arréglalo** |
| **`suggestion`** | una sugerencia | valora si te aplica |

!!! note "La nota es una guía, no un objetivo"
    No hay que llegar a 100: muchas sugerencias no aplican a un servidor concreto (particiones, HTTPS, paquetes de
    escritorio…). Lo importante es **entender cada aviso y decidir**, no inflar el número.

## 🔐 2. SSH: la puerta principal

SSH es por donde se administra el servidor. Cuatro cerrojos:

```bash title="servidor/ssh/bastionado.conf" linenums="1"
PermitRootLogin no
PasswordAuthentication no
MaxAuthTries 3
X11Forwarding no
```

| Línea | Para qué |
|---|---|
| `PermitRootLogin no` | `root` **no entra directamente**: se entra con un usuario normal y luego `sudo` (así queda apuntado **quién** ha sido) |
| `PasswordAuthentication no` | solo con **llave** (la de la UD4: privada en tu equipo, pública en el servidor). Una contraseña se adivina; una llave, no |
| `MaxAuthTries 3` | como mucho **3 intentos** por conexión |
| `X11Forwarding no` | ventanas gráficas remotas: en un servidor, no hacen falta |

!!! tip "¿Dónde va, y por qué el fichero manda"
    No se toca `/etc/ssh/sshd_config`. Se crea un fichero en **`/etc/ssh/sshd_config.d/`** que **acabe en `.conf`** (en
    el laboratorio, `servidor/ssh/bastionado.conf`). SSH se queda con el **primer valor** que lee de cada opción, y
    `sshd_config.d/` se lee **antes**. Después: `./lab.sh ssh` (comprueba con `sshd -t` y, si está bien, recarga).

### 2.1 Demo — la misma orden, antes y después

```bash title="Antes (./lab.sh internet)"
sshpass -p bodega2026 ssh root@10.10.20.30 whoami
root
```

```bash title="Después"
sshpass -p bodega2026 ssh root@10.10.20.30 whoami
root@10.10.20.30: Permission denied (publickey).
```

`(publickey)` = el servidor **ya ni pregunta** la contraseña, solo admite llave. Y el administrador **sigue entrando**
con la suya:

```bash
ssh admin@10.10.20.30 whoami     # → admin
```

`sshd -T` enseña la configuración que SSH está usando **de verdad** (no lo que crees que pusiste):

```bash title="sshd -T | grep -E '^(permitrootlogin|passwordauthentication|maxauthtries|x11forwarding) '"
permitrootlogin no
passwordauthentication no
maxauthtries 3
x11forwarding no
```

!!! danger "No te quedes fuera"
    Si cierras las contraseñas y tu llave **no está** en el servidor, **nadie vuelve a entrar** (ni tú). Orden seguro:

    1. Copia tu llave pública al servidor (`ssh-copy-id admin@servidor`).
    2. Comprueba que **entras con la llave** en **otra** terminal.
    3. **Solo entonces** pones `PasswordAuthentication no` y recargas.
    4. Vuelve a probar en otra terminal, **sin cerrar** la sesión que tienes abierta.

## ⚙️ 3. El núcleo y las cuentas

### 3.1 El núcleo: `sysctl`

El núcleo (kernel) también se ajusta. Tres opciones que importan y se entienden:

```bash title="servidor/sysctl.d/99-bastionado.conf" linenums="1"
kernel.randomize_va_space = 2
kernel.dmesg_restrict = 1
net.ipv4.conf.all.accept_redirects = 0
```

| Ajuste | Para qué |
|---|---|
| `kernel.randomize_va_space = 2` | **ASLR completo**: cada programa se carga en direcciones de memoria al azar; a un atacante le cuesta mucho más aprovechar un fallo |
| `kernel.dmesg_restrict = 1` | los mensajes del núcleo, **solo para root** (dan pistas al atacante) |
| `net.ipv4.conf.all.accept_redirects = 0` | no hacer caso a los **ICMP redirect**, con los que alguien de la red podría desviar nuestro tráfico |

!!! note "En el laboratorio no se aplica, se revisa"
    En un servidor de verdad, `sysctl --system` aplica el fichero. En el laboratorio el núcleo es el de **tu ordenador**
    (Docker lo comparte), así que solo se **escribe y se revisa** el fichero; no se aplica.

### 3.2 Cuentas y permisos: llaves maestras escondidas

**UID 0.** El sistema no mira el **nombre**, mira el **número**. Quien tenga UID 0 es `root`, se llame como se llame:

```bash title="¿quién tiene UID 0?"
awk -F: '$3==0' /etc/passwd
root:x:0:0:root:/root:/bin/bash
soporte:x:0:0::/root:/bin/bash        ← una llave maestra escondida
```

**SUID.** Un programa con el bit **SUID** se ejecuta **como su dueño** (`root`), lo lance quien lo lance. `passwd` lo
necesita (tiene que escribir `/etc/shadow`); pero uno **desconocido en `/usr/local`** es una **puerta trasera**:
cualquier usuario sería root.

```bash title="¿qué programas tienen SUID?"
find / -xdev -perm -4000 -type f 2>/dev/null
/usr/lib/openssh/ssh-keysign
/usr/local/bin/copia-seguridad        ← este no es del sistema: sospechoso
/usr/bin/passwd
/usr/bin/su
...
```

| Qué | Arreglo |
|---|---|
| La cuenta `soporte` con UID 0 | borrarla (`userdel soporte`) o quitarle el UID 0 |
| El SUID de `copia-seguridad` | quitarle el bit (`chmod u-s`) o borrar el programa |

!!! tip "SUID normal frente a SUID sospechoso"
    `passwd`, `su`, `mount`, `sudo` llevan SUID **a propósito**: son del sistema. El sospechoso es el que **no conoces**
    y está donde no debería (`/usr/local`, `/home`, `/tmp`).

## 🌐 4. Nginx: el servicio web

Dos cosas en `servidor/nginx/seguridad.conf`:

```nginx title="servidor/nginx/seguridad.conf" linenums="1"
server_tokens off;
add_header X-Frame-Options "DENY" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Content-Security-Policy "default-src 'self'" always;
```

| Línea | Para qué |
|---|---|
| `server_tokens off` | que **no diga la versión**: el atacante no sabe qué fallos buscarle |
| `X-Frame-Options "DENY"` | que **nadie meta** nuestra web en un marco (`iframe`) para engañar al usuario con clics (*clickjacking*) |
| `X-Content-Type-Options "nosniff"` | que el navegador **no adivine** el tipo de un fichero (un `.jpg` que en realidad es JavaScript) |
| `Content-Security-Policy "default-src 'self'"` | solo cargar cosas de **nuestra propia web**: frena mucho el XSS (UD5) |
| `always` | que se manden **también** en las páginas de error (404, 500…) |

!!! note "Las cabeceras son instrucciones para el navegador"
    `server_tokens` cambia lo que dice el servidor; las `add_header` son **instrucciones que el servidor le da al
    navegador del cliente**. No arreglan un fallo del código, pero cierran formas de abusar de él.

### 4.1 Demo — `curl -I`, antes y después

`curl -I` pide solo las **cabeceras** de la respuesta (lo que ve el atacante):

```bash title="Antes"
HTTP/1.1 200 OK
Server: nginx/1.26.3
...
```

```bash title="Después (./lab.sh nginx)"
HTTP/1.1 200 OK
Server: nginx
...
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Content-Security-Policy: default-src 'self'
```

Después: `./lab.sh nginx` (comprueba con `nginx -t` y recarga).

## 🚪 5. Fail2ban: el portero

**Fail2ban** apunta al que prueba llaves y lo deja fuera. Cómo funciona, cuatro pasos:

```text
1 lee el registro   →  2 busca los fallos  →  3 cuenta por IP  →  4 banea
  /var/log/auth.log      el filtro de SSH       maxretry en          regla en
                                                 findtime             nftables (UD3)
```

Cuando una IP falla `maxretry` veces en `findtime`, Fail2ban la **banea** durante `bantime`: añade una regla al
cortafuegos (**nftables**, UD3) que la deja fuera. Una **cárcel** (*jail*) es esa configuración para un servicio.

```ini title="servidor/fail2ban/jail.local" linenums="1"
[sshd]
enabled  = true
logpath  = /var/log/auth.log
maxretry = 3
findtime = 10m
bantime  = 1h
```

| Campo | Qué es |
|---|---|
| `enabled = true` | activa la cárcel (venía en `false`) |
| `maxretry` · `findtime` | 3 fallos en 10 minutos… |
| `bantime` | …1 hora fuera |

!!! warning "`jail.local`, nunca `jail.conf`"
    `jail.conf` se **machaca** al actualizar el paquete. Tu configuración va siempre en `jail.local`, que no se toca.
    Después: `./lab.sh fail2ban`.

### 5.1 Demo — cinco intentos y fuera

Desde `internet`, cinco usuarios inventados. Los primeros contestan `Permission denied`; al tercero ya no hay conexión:
el portero lo ha echado.

```bash title="fail2ban-client status sshd"
Status for the jail: sshd
|- Filter
|  `- Total failed:     7
`- Actions
   |- Currently banned: 1
   `- Banned IP list:   203.0.113.50
```

```bash title="nft list ruleset  (lo que ha puesto Fail2ban en el cortafuegos)"
set addr-set-sshd {
    elements = { 203.0.113.50 }
}
tcp dport 22 ip saddr @addr-set-sshd reject
```

!!! tip "Quitar el castigo y no banearte a ti mismo"
    `fail2ban-client unban --all` quita los baneos. En un servidor de verdad, pon **tu IP** en `ignoreip` para no
    banearte tú mismo administrando.

## 📏 6. Volver a medir, y las guías

### 6.1 La nota, antes y después

Con todo lo de la unidad hecho (`./lab.sh comprobar ud6` en verde), Lynis sube:

```text
Antes:    58 / 100   ·   warning: Fail2ban sin cárceles
Después:  63 / 100   ·   warning: ninguno
```

Han desaparecido el aviso de Fail2ban y las sugerencias de `PermitRootLogin`, `MaxAuthTries` y `X11Forwarding`. **¿Por
qué no 100?** Porque Lynis revisa cosas que aquí no tocamos (particiones, paquetes, HTTPS) o que no aplican en un
contenedor. Lo importante es que **cada aviso que queda está entendido y decidido**.

### 6.2 No nos lo inventamos: hay guías

| Guía | Qué es |
|---|---|
| **CIS Benchmarks** (Center for Internet Security) | guías internacionales y gratuitas, una por sistema (Debian, Nginx, SSH…), con **nivel 1** (lo básico, sin romper nada) y **nivel 2** (más estricto) |
| **CCN-STIC** (Centro Criptológico Nacional, España) | las guías que siguen las administraciones públicas para cumplir el **Esquema Nacional de Seguridad (ENS)** |

!!! note "Bastionar en una empresa"
    Elegir una guía → aplicarla → **documentar lo que NO se aplica y por qué** → medir (Lynis). La documentación es
    parte del trabajo: el ENS es obligatorio en la administración pública española.

## ⚠️ 7. Errores típicos

| Error | Qué pasa | Bien |
|---|---|---|
| Cerrar contraseñas sin llave en el servidor | **nadie vuelve a entrar, ni tú** | copiar llave → probar → cerrar |
| Un fichero que no acaba en `.conf` | SSH (o Nginx) no lo lee | `sshd_config.d/bastionado.conf` |
| La cárcel sin activar | Fail2ban arrancado… sin portero | `[sshd]  enabled = true` |
| Cabeceras sin `always` | no se mandan en las páginas de error | `add_header ... "DENY" always;` |
| Confiar en la nota de Lynis | 100 no es el objetivo | entender cada aviso |

## 📋 9. Glosario rápido

| Término | Qué es |
|---|---|
| **Bastionar (hardening)** | reducir la superficie de ataque de un sistema |
| **Superficie de ataque** | todo lo que un atacante podría usar para entrar |
| **Hardening index** | la nota de 0 a 100 que da Lynis |
| **`sshd_config.d/`** | carpeta de ficheros `.conf` que manda sobre `sshd_config` |
| **UID 0** | identificador de `root`; el nombre no importa, el número sí |
| **SUID** | bit que hace que un programa se ejecute como su dueño |
| **`sysctl` / ASLR** | ajustes del núcleo / cargar los programas en memoria al azar |
| **Cabeceras de seguridad** | instrucciones de Nginx al navegador (X-Frame-Options, CSP…) |
| **Fail2ban / jail** | el portero que banea por fallos / su configuración para un servicio |
| **CIS / CCN-STIC / ENS** | guías de bastionado / guías españolas / el esquema que obliga a seguirlas |
